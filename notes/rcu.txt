🔹 What is RCU in DPDK?

RCU = Read-Copy-Update

It is a lockless synchronization mechanism used to safely share data between:

multiple readers (fast path – packet processing)
and writers (control plane / updates)

👉 Core idea:

Readers never take locks. Writers update data by creating a copy.

🔹 Why do we need RCU in DPDK?

DPDK is all about:

🚀 ultra-fast packet processing
⚡ multi-core parallel execution
❌ avoiding locks (because locks = slow)
❌ Problem WITHOUT RCU

Let’s say you have a routing table shared across cores:

Core 0 → reading (processing packets)
Core 1 → updating (adding/deleting routes)
Old approach:
lock();
read or write;
unlock();
🚨 Issues:
Lock contention (many cores waiting)
Packet drops due to delays
Poor scalability
🔹 What we were doing earlier (before RCU)
1. Spinlocks / Mutex
rte_spinlock_lock(&lock);
access shared data;
rte_spinlock_unlock(&lock);

👉 Problem:

Readers blocked by writers
Not scalable for many cores
2. Reader-Writer Locks
Many readers allowed
Writer blocks all readers

👉 Still a problem:

Writer pauses packet processing
🔹 RCU Solution (Concept)

Instead of modifying shared data directly:

✅ Writer:
Creates a copy
Modifies the copy
Atomically swaps pointer
✅ Reader:
Always reads without lock
Uses old or new version safely
🔹 Simple Analogy (Very Important)

Think of a library book 📚:

Readers → reading book
Writer → wants to update content
Without RCU:
Writer takes book → no one can read ❌
With RCU:
Writer creates a new copy of book
Updates it
Replaces old book on shelf
Old readers still reading old copy safely ✅
🔹 How RCU Works Internally

RCU has 3 main steps:

1. Read Phase (No Lock 🚀)
rcu_read_lock();
data = global_ptr;
use(data);
rcu_read_unlock();

👉 Readers:

No blocking
Super fast
2. Update Phase (Copy + Replace)
new_data = copy(old_data);
modify(new_data);
global_ptr = new_data;

👉 Important:

Old data is still being used by readers
3. Grace Period (Cleanup)

👉 Wait until all old readers finish

Then:

free(old_data);
🔹 RCU in DPDK (Actual APIs)

DPDK provides RCU APIs like:

1. Read-side APIs
rte_rcu_qsbr_thread_register();
rte_rcu_qsbr_thread_online();
rte_rcu_qsbr_thread_offline();
2. Quiescent State Reporting
rte_rcu_qsbr_quiescent();

👉 Meaning:

"This thread is done with old data"

3. Synchronization
rte_rcu_qsbr_synchronize();

👉 Wait until:

All readers finish using old version
🔹 Example in DPDK Context
Use Case: Routing Table Update
Reader (packet processing core)
rcu_read_lock();
route = lookup_route(table, ip);
rcu_read_unlock();
Writer (control plane)
new_table = copy(old_table);
update(new_table);
global_table = new_table;

rte_rcu_qsbr_synchronize();  // wait for readers
free(old_table);
🔹 Why RCU is Powerful in DPDK
✅ Advantages
🚀 Zero lock in read path
⚡ Extremely fast packet processing
📈 Scales with many cores
🔥 Perfect for read-heavy workloads
❗ Trade-offs
More memory usage (copies)
Complex to implement correctly
Writers are slower
🔹 When to Use RCU in DPDK

Use RCU when:

✔ Reads are very frequent (packet path)
✔ Writes are rare (config updates)
✔ Need high scalability
🔹 When NOT to Use
❌ Frequent writes
❌ Memory is very limited
❌ Simple single-threaded case
🔥 Key Insight (Most Important)

👉 In DPDK:

Packet processing MUST NEVER WAIT

That’s why:

Locks ❌
RCU ✅
🔹 Quick Comparison
Method	Read Speed	Write Speed	Scalability
Mutex	Slow	Slow	Poor
RW Lock	Medium	Slow	Medium
RCU	🔥 Fast	Medium	🚀 Excellent
🔹 Final Summary
RCU = lockless read synchronization
Readers → no lock, super fast
Writers → copy + replace
Old data freed after grace period




🔹 1. The Real Problem at CPU Level

Even if your logic is correct, CPUs can still break it due to:

⚠️ 1. Reordering

CPU may reorder instructions like:

new->field = value;
global_ptr = new;

👉 CPU might do:

global_ptr = new;   // happens first ❌
new->field = value; // happens later ❌

💥 Now readers see partially initialized data

⚠️ 2. Cache Visibility (Multi-core issue)

Each core has its own cache.

Core 1 (writer) updates data
Core 2 (reader) may still see old cached values

💥 Leads to inconsistent reads

🔹 2. Solution: Memory Barriers + Atomic Ops

RCU relies on two key concepts:

✅ (A) Atomic Pointer Update

Pointer swap must be atomic

👉 Meaning:

Reader sees either:
old pointer
OR new pointer
❌ never a half-written pointer
✅ (B) Memory Ordering (Barriers)

We enforce:

👉 “All writes to new data must be visible BEFORE pointer update”

🔹 3. The Correct CPU-Level Sequence
Writer does:
new = copy(old);
new->field = value;

👉 These writes go to cache/store buffer

🚨 Critical Step: Write Memory Barrier
rte_smp_wmb();

👉 Ensures:

All previous writes (to new) are globally visible
BEFORE next operation
🔥 Then Pointer Swap
global_ptr = new;   // atomic store
🔹 4. What Reader Does
ptr = global_ptr;

Then:

rte_smp_rmb();
use(ptr);
Why Read Barrier?

Ensures:

Pointer is read first
Then actual data is read

👉 Prevents CPU from doing:

read data first ❌
then read pointer ❌
🔹 5. Why Pointer Swap is Safe Across Cores

Let’s break it down carefully.

🔸 Case 1: Reader sees OLD pointer
ptr = DATA_V1;

👉 Safe because:

Writer never modified DATA_V1
🔸 Case 2: Reader sees NEW pointer
ptr = DATA_V2;

👉 Safe because:

Memory barrier ensured DATA_V2 is fully initialized
🔥 Key Guarantee

👉 If a reader sees the new pointer, it is guaranteed to see fully initialized data.

🔹 6. What Makes This Work (Hardware Level)
Modern CPUs provide:
✅ Cache Coherency Protocol (MESI)
Ensures all cores eventually see consistent memory
When pointer is updated:
Cache line is invalidated on other cores
✅ Atomic Store Instructions

Pointer update uses:

single aligned write (usually 64-bit)

👉 Hardware guarantees:

no tearing (no half pointer)
🔹 7. DPDK-Specific Implementation

DPDK uses macros like:

rte_rcu_assign_pointer(p, v);

Internally does:

write barrier
atomic store

Reader side:

p = rte_rcu_dereference(ptr);

Internally:

read barrier
safe load
🔹 8. Full Timeline (CPU Level)
Core 1 (Writer)                Core 2 (Reader)

write new->field
write new->field
rte_smp_wmb()  ------------>   (ensures visibility)

global_ptr = new  ---------->  read global_ptr

                              rte_smp_rmb()

                              read new->field (correct value)
🔥 9. What If We REMOVE Barriers? (Very Important)

Then this can happen:

Writer: global_ptr = new
Reader: ptr = new
Reader: reads uninitialized fields 💥
Writer: initializes fields later

👉 This is the exact bug RCU prevents

🔹 10. Final Mental Model

Think like this:

🧠 Pointer = "publish signal"
📦 Data = "payload"

👉 Rule:

Payload must be ready BEFORE publish
🔥 Final Answer
❓ Why pointer swap is safe across cores?

Because:

Pointer update is atomic → no partial pointer
Write memory barrier ensures:
data is fully written before pointer update
Read barrier ensures:
pointer is read before data access
Cache coherency ensures visibility across cores
🔹 One-Line Summary

💡 RCU works because it combines atomic pointer swap + strict memory ordering, 
ensuring readers always see fully consistent data across all CPU cores.

🔹 What is a Quiescent State?

👉 Simple definition:

💡 A quiescent state is a point where a thread guarantees:
“I am NOT using any old RCU-protected data anymore.”

🔹 Why Do We Need It?

Remember the writer does:

Replace pointer
Wait for readers
Free old data

👉 The big question is:

❓ How does the writer know that no reader is still using old data?

👉 Answer: Quiescent state

🔹 Intuition (Very Simple)

Think like this:

Reader:
Reads old data
Finishes work
Says → “I’m done ✅”

👉 That “I’m done” = quiescent state

🔹 In Your Code
rte_rcu_qsbr_quiescent(qsbr, id);

👉 This line means:

“From this point onward, I will NOT access any old version of data.”

🔹 Timeline Example (Very Important)
Time →
------------------------------------------------------

Reader:   read old data ----- DONE ---- quiescent()

Writer:        swap pointer → wait → free old
🔹 What Happens Internally

Each thread has a state counter / epoch

When you call:

rte_rcu_qsbr_quiescent()

👉 It updates your thread state to:

“I have passed a safe point”

🔹 Writer Side
rte_rcu_qsbr_synchronize()

👉 Writer waits until:

✔ All threads have reported quiescent state
✔ Meaning none are using old data

🔥 Key Guarantee

💡 After all threads reach quiescent state → old memory is safe to free

🔹 What is NOT a Quiescent State?

If reader is doing this:

struct data *d = gdata;
use(d);

👉 ❌ NOT quiescent
👉 Because it might still be using old data

🔹 What IS a Quiescent State?

After finishing:

use(d);

👉 Then:

rte_rcu_qsbr_quiescent();

👉 ✅ Now safe

🔹 Real-Life Analogy

Imagine workers using a shared document:

Writer wants to delete old version
Workers say:
“I’m still reading ❌”
“I’m done reading ✅” ← quiescent state

👉 Writer waits until ALL say “done”

🔹 Important Detail (Very Important)

👉 Quiescent state does NOT mean:

Thread stopped
Thread idle

👉 It only means:

“I have passed a point where I don’t hold old references”

🔹 In DPDK (Why Explicit?)

In Linux kernel:

Scheduler tracks this automatically

In DPDK:

No preemption
No scheduler tracking

👉 So YOU must explicitly say:

rte_rcu_qsbr_quiescent()
🔥 What If You Forget It?

👉 Writer will:

rte_rcu_qsbr_synchronize()

❌ Wait forever
❌ Memory leak / stall

🔹 Mental Model (Best Way to Remember)

🧠 Quiescent state = “checkpoint where thread guarantees it dropped all old references”

🔥 Final One-Line Answer

💡 A quiescent state is a point where a thread guarantees it is no longer accessing any old
 RCU-protected data, allowing the writer to safely free that data.

 🔹 What is QSBR?

👉 QSBR = Quiescent State Based Reclamation

It is a type of RCU mechanism used in systems like DPDK to safely free memory without locks.

🔥 Simple Definition

💡 QSBR is a method where threads explicitly tell the system when they are done using old data.

🔹 Break the Name (Very Important)
1. Quiescent State

👉 Thread says:

“I am not using old data anymore”

2. Based

👉 System depends on these signals

3. Reclamation

👉 Safe freeing of old memory

🔹 Why QSBR is Needed in DPDK

DPDK:

No OS scheduler involvement
No preemption
Threads run continuously (polling)

👉 So system cannot automatically detect:

“Is a thread still using old data?”

👉 Solution:

🔥 Threads manually report → QSBR

🔹 How QSBR Works (Step-by-Step)
🟢 Step 1: Reader reads data
d = gdata;
🟡 Step 2: Reader finishes
rte_rcu_qsbr_quiescent(qsbr, id);

👉 Means:

“I am done with old references”

🔵 Step 3: Writer updates pointer
global_ptr = new_data;
🔴 Step 4: Writer waits
rte_rcu_qsbr_synchronize(qsbr, ...);

👉 Waits until:

ALL threads report quiescent state
⚫ Step 5: Free old data
rte_free(old_data);
🔹 Visual Timeline
Time →
------------------------------------------------------

Reader:   read old ---- done ---- quiescent()

Writer:        swap → wait → free old
🔹 Key Idea

💡 QSBR tracks “who might still be using old data”

🔹 What QSBR Actually Tracks Internally

👉 For each thread:

Registered thread ID
State (active / quiescent)
Epoch / counter

👉 Writer checks:

“Has every thread passed a quiescent state after my update?”

🔹 APIs You Use
✅ Register thread
rte_rcu_qsbr_thread_register(qsbr, id);
✅ Mark active
rte_rcu_qsbr_thread_online(qsbr, id);
✅ Report safe point
rte_rcu_qsbr_quiescent(qsbr, id);
✅ Wait for all readers
rte_rcu_qsbr_synchronize(qsbr, ...);
✅ Remove thread
rte_rcu_qsbr_thread_unregister(qsbr, id);
🔹 Why QSBR is Fast 🚀

👉 No locks
👉 No tracking per read
👉 No kernel involvement

Only:

Occasional quiescent() calls
🔹 Compare QSBR vs Other RCU
Feature	QSBR (DPDK)	Linux RCU
Tracking	Manual	Automatic
Preemption	❌ No	✅ Yes
Overhead	🔥 Very low	Medium
Control	User-controlled	Kernel-controlled
🔴 Important Rule

❗ If a thread never reports quiescent state → writer blocks forever

🔹 Real-Life Analogy

Imagine workers using a shared file:

Writer: “Can I delete old version?”
Workers:
“Still using ❌”
“Done ✅” ← quiescent

👉 QSBR = system tracking these “done” signals

🔥 Final One-Line Answer

💡 QSBR (Quiescent State Based Reclamation) is an RCU technique where threads explicitly report when they are done using old data, allowing safe memory reclamation without locks.

🔹 Super Important Insight

🧠 QSBR is NOT about reading
🧠 It is about knowing when it is safe to free old memory
