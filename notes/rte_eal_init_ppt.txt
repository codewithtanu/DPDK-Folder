1. MMU Check (eal_mmu_supported())
What the MMU is

The Memory Management Unit (MMU) is hardware in the CPU that translates:

Virtual Address → Physical Address

Modern operating systems use virtual memory, so applications never directly access physical memory.

Example:

Application address : 0x7ffd12340000
MMU translates      : 0x3a001234000
Why DPDK checks MMU support

DPDK relies heavily on:

hugepage memory

memory mapping (mmap)

DMA access for NIC devices

Without an MMU, these things cannot work.

For example:

NIC DMA → physical memory

But the application sees:

virtual memory

The MMU (and sometimes IOMMU) allows the mapping.

So DPDK verifies:

Does the architecture support the required memory mapping model?
What eal_mmu_supported() checks

The function checks whether the system supports IOVA addressing modes.

Two main modes exist:

Mode	Meaning
IOVA = PA	device sees physical addresses
IOVA = VA	device sees virtual addresses

DPDK must ensure that one of these works correctly.

Internally the function checks:

architecture type
memory translation mode
kernel support

If unsupported:

EAL: unsupported MMU type

Initialization stops.

Good question — this is the key concept of how DPDK accesses hugepage memory. Let’s explain it clearly.

You asked:

Hugepages are physical memory. They are mapped with what? And then memsegs store the mapping info?

Yes — that idea is mostly correct. Let’s walk through the exact mapping chain.

1. Where Hugepages Exist Initially

When the system boots with:

hugepages=1024 hugepagesz=2M

the Linux kernel reserves physical memory.

Example:

Physical RAM
│
├─ Hugepage (2MB)  → Physical address 0x20000000
├─ Hugepage (2MB)  → Physical address 0x20200000
├─ Hugepage (2MB)
└─ ...

These are physical pages managed by the kernel.

2. Hugepages Appear as Files in hugetlbfs

Hugepages are exposed through the hugetlbfs filesystem.

Example mount:

/dev/hugepages

DPDK creates files like:

/dev/hugepages/rtemap_0
/dev/hugepages/rtemap_1

Each file corresponds to a hugepage-backed memory region.

So now the chain becomes:

Physical Hugepage
        ↓
hugetlbfs file
3. DPDK Maps the Hugepage File Using mmap()

Inside rte_eal_memory_init() DPDK does:

mmap()

Conceptually:

virtual_addr = mmap(NULL, hugepage_size, ..., fd)

This maps the hugepage file into the process virtual address space.

Now the chain becomes:

Physical Hugepage
       ↓
hugetlbfs file
       ↓
mmap()
       ↓
Virtual address in DPDK process

Example:

Physical: 0x20000000
Virtual:  0x7f8000000000

Now the application can access that memory.

4. What Memseg Stores

After mapping, DPDK creates a memseg descriptor.

A memseg stores metadata about that mapped memory.

Example memseg entry:

memseg
│
├─ virtual_addr = 0x7f8000000000
├─ phys_addr    = 0x20000000
├─ length       = 2MB
└─ socket_id    = 0

So memseg stores:

virtual address
physical address
size
NUMA node

This allows DPDK to manage the hugepage memory.

5. Visualization of the Whole Flow
Kernel reserves hugepages
        │
        ▼
Physical hugepage (2MB)
        │
        ▼
hugetlbfs file (/dev/hugepages/rtemap_0)
        │
        ▼
mmap()
        │
        ▼
Virtual address in DPDK process
        │
        ▼
memseg descriptor created
6. Why This Mapping Is Necessary

Applications run in virtual memory, not physical memory.

So DPDK must map hugepages into the process address space.

Benefits:

fast packet buffers
DMA-capable memory
NUMA awareness
7. After Memsegs Are Created

Then the memory hierarchy continues:

Hugepages
     ↓
memsegs
     ↓
memzones
     ↓
mempools
     ↓
mbufs

=================================================================================================

Hugepage Mapping Flow in DPDK

Kernel reserves hugepages at boot time (e.g., hugepages=1024 hugepagesz=2M).
These are contiguous physical memory pages.

The kernel exposes these pages through the hugetlbfs filesystem (e.g., /dev/hugepages).

DPDK opens these hugepage files and maps them into the process address space using the mmap() system call.

After mapping, DPDK creates memseg descriptors that store metadata about each mapped memory segment, including:

virtual address

physical address

page size

NUMA socket

These memsegs are then used to build higher-level memory structures:

Hugepages
   ↓
memsegs
   ↓
memzones
   ↓
mempools
   ↓
mbufs / rings / other objects

In short:
Hugepages are physical memory reserved by the kernel, mapped into the DPDK application's virtual address space
using mmap(), and memseg structures store the mapping information used to manage that memory.
